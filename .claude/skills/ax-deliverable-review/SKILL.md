# AX Deliverable Review

문서 하나의 품질이 아니라 **문서 묶음이 한 목소리를 내는가**를 검수한다.

## 왜 경계면인가
각 문서를 다른 에이전트가 썼으면 개별 품질은 높아도 경계면에서 어긋난다. 기획서가 약속한 KPI가 전략 문서와 다르거나, GDD의 시스템 하나가 빌드 플랜에 태스크가 없는 식이다. 고객은 그 어긋남을 가장 먼저 본다.

## 절차
1. 산출물 목록과 각 문서의 핵심 값을 먼저 추출한다: KPI 목록, 시나리오 명칭, 병목 상위 5 순서, 우선순위 1~3, GDD 시스템 목록, 태스크 id 목록, 거버넌스 문서 목록, 로드맵 단계·기간.
2. `references/checklist.md`의 항목을 순서대로 적용한다. 각 발견에 파일·절·인용·수정 제안을 붙인다.
3. 심각도 분류: **차단**(사실 오류·측정 불가 약속·규제 오해·GDD 시스템 무대응·수용 기준 없음) / **중요**(용어 불일치·순위 불일치·추정 표시 누락) / **권고**(분량·톤).
4. 리포트 작성 후 차단·중요 항목을 원저자에게 전달한다. 원저자 응답이 불가한 모드에서는 리더가 직접 반영할 수 있게 수정 제안을 완결형으로 쓴다.
5. 재검수는 변경된 경계면만 다시 본다.

## 리포트 템플릿

```markdown
# 검수 리포트 — {대상사} AX 산출물 v{n}
## 1. 검수 범위와 추출 값 요약표
## 2. 차단 (파일 · 절 · 인용 · 수정 제안)
## 3. 중요
## 4. 권고
## 5. GDD 시스템 ↔ 태스크 대응표 검증 결과
## 6. 첫 미팅 확인 항목으로 승격한 가정 목록
## 7. 잔여 리스크와 재검수 필요 여부
```
