Codex Build Spec

GDD를 코딩 에이전트가 검증 가능한 태스크 단위로 자율 구현할 수 있는 스펙으로 바꾼다.

왜 이 구조인가

코딩 에이전트는 모호함에 약하고 테스트로 완료를 증명할 수 있는 작업에 강하다. 그래서 (1) 렌더링 없는 결정적 코어를 먼저 만들어 모든 규칙을 유닛 테스트로 고정하고, (2) 그 코어를 그대로 돌리는 헤드리스 시뮬레이터로 밸런스를 회귀 테스트하고, (3) 마지막에 렌더러를 붙인다. 이 순서는 컨설팅의 QA AX 원칙(시뮬레이터-퍼스트)을 신작에서 리팩터링 없이 구현하는 방법이기도 하다.

기본 스택 선택

  • 기본 트랙: TypeScript 모노레포 — packages/core(순수 룰, 의존성 0), packages/sim(헤드리스 CLI), apps/web(PixiJS 또는 Canvas 렌더러, PWA). 코딩 에이전트가 샌드박스에서 npm test·npm run sim·Playwright 스크린샷까지 스스로 검증할 수 있어 자율성이 유지된다.
  • 2차 트랙: Unity/C# 포팅 — 코어 룰을 C# 클래스 라이브러리로 1:1 포팅, 동일 JSON 테이블 사용. 스튜디오의 실제 스택이 Unity인 경우 프로토타입 검증 후 진행.
  • 스택을 바꿔야 할 이유가 있으면 바꾸되, "코어 무의존·시드 RNG·JSON 테이블·헤드리스 시뮬레이터" 네 원칙은 유지한다.

절차

1. 아키텍처 절

패키지 경계, 의존 방향(web→core, sim→core, core→없음), 시드 RNG 단일 소스, 틱 기반 시뮬레이션(고정 dt, 예: 100ms), 저장 포맷(버전 필드 포함), 테이블 로딩 방식을 쓴다. 다이어그램 1개.

2. 데이터 테이블 스키마

GDD 8장의 스키마를 JSON Schema 수준으로 옮기고 data/*.json 파일 목록과 초기 행 수(MVP)를 정한다. 밸런스 파라미터(g_hp, g_cost 등)는 data/balance.json 한 파일에 모은다. 하드코딩 금지 규칙을 AGENTS.md에 넣는다.

3. Phase별 태스크 카드

references/task-card-format.md 형식으로 Phase 0(스캐폴드) → 1(코어 룰) → 2(시뮬레이터·밸런스 회귀) → 3(저장·오프라인·프레스티지) → 4(렌더러 MVP) → 5(수익모델·광고 스텁·분석 이벤트) → 6(콘텐츠 확장·폴리시)를 분해한다. 태스크 1개 = 코딩 에이전트 1세션. 수용 기준은 반드시 실행 명령과 기대 결과로 쓴다. GDD의 모든 시스템이 최소 1개 태스크에 대응되는지 대응표를 만든다.

4. 시뮬레이터 설계

봇 전략 3종(균형: 가장 싼 강화 우선 / 공격: ATK 집중 / 방치: 접속 3회·오프라인 위주), 가상 일정(D1·D3·D7·D30 압축 실행), 출력(도달 스테이지·벽 시각·프레스티지 횟수·골드 곡선 CSV), 회귀 테스트(목표 벽 표 ±10%, 확률 표기 검증 N=100k). npm run sim -- --days 7 --bot balanced --seed 42 형태의 CLI를 명세한다.

5. AGENTS.md

references/agents-md-template.md를 채운다. 실행·테스트 명령, 코딩 컨벤션, 금지(하드코딩 수치·Math.random 직접 호출·core에서 DOM 접근), 완료 정의(테스트 통과 + 시뮬레이터 회귀 통과 + 변경 요약), 질문이 생길 때의 행동(GDD의 "가정 목록"에 추가하고 진행).

6. 실행 가이드

사용자가 Codex에 넘기는 순서: 저장소 생성 → AGENTS.md·GDD·빌드 플랜·data/ 배치 → Phase 0 태스크부터 순서대로 프롬프트 → 각 태스크 후 수용 기준 명령 실행 → 회귀 실패 시 밸런스 파라미터 조정은 GDD 담당이 결정. 프롬프트 예시 2개를 포함한다.

출력 템플릿

# {게임명} Codex 빌드 플랜
## 1. 아키텍처 (다이어그램·의존 규칙·RNG·틱·저장)

AGENTS.md 템플릿

### AGENTS.md — {게임명} 프로토타입

### 이 저장소는
{한 문장}. 기획 문서는 `docs/GDD.md`, 밸런스 수식은 `docs/BALANCE.md`, 태스크는 `docs/BUILD_PLAN.md`. 코드보다 문서가 우선이며, 문서와 코드가 다르면 문서를 고치지 말고 이슈로 남긴 뒤 문서를 따른다.

### 구조
- `packages/core` — 순수 게임 룰. 외부 의존성 0. DOM·타이머·네트워크·`Math.random` 금지.
- `packages/sim` — 헤드리스 시뮬레이터 CLI. core만 의존.
- `apps/web` — 렌더러(PixiJS). core만 의존. 룰을 여기서 구현하지 않는다.
- `data/*.json` — 모든 콘텐츠·밸런스 테이블. 코드에 수치를 하드코딩하지 않는다.

### 명령
- 설치: `npm ci`
- 전체 테스트: `npm test`
- 코어만: `npm test -w packages/core`
- 시뮬레이터: `npm run sim -- --days 7 --bot balanced --seed 42`
- 회귀: `npm run sim:regress` (목표 벽 표 ±10%, 확률 검증)
- 웹 실행: `npm run dev -w apps/web` / 스크린샷: `npm run e2e`

### 규칙
- 난수는 `core/rng.ts`의 시드 RNG만 사용. 같은 시드 = 같은 결과.
- 시뮬레이션은 고정 틱(100ms). 프레임 시간에 의존하는 룰 금지.
- 저장 데이터에는 `schemaVersion` 필드. 마이그레이션 함수 없이 필드 변경 금지.
- 새 콘텐츠는 테이블 행 추가로만. 타입/스키마 변경은 `data/schema/*.json` 갱신 + 테스트 동반.
- 커밋 단위 = 태스크 카드 1개. 메시지 앞에 태스크 id (`T1.3: …`).

### 완료 정의
1. 태스크 카드의 수용 기준 명령이 모두 통과
2. `npm test` 전체 통과, `npm run sim:regress` 통과(밸런스 관련 변경 시)
3. 변경 요약 3줄 + 새로 생긴 가정은 `docs/ASSUMPTIONS.md`에 추가

### 막히면
규칙이 GDD에 없으면 임의로 정하지 말고 `docs/ASSUMPTIONS.md`에 "가정: …" 을 추가하고 가장 보수적인 선택으로 진행한다. 밸런스 파라미터 값은 바꾸지 않는다(기획 담당 결정).

참조 문서: references/task-card-format.md

태스크 카드 형식

### T{phase}.{n} {제목}
- 목표: 한 문장
- 의존: T… (없으면 없음)
- 입력: 읽어야 할 파일·GDD 절
- 산출: 생성/수정 파일 목록
- 규칙: 이 태스크에서 지켜야 할 GDD 규칙 인용(수식·표)
- 수용 기준:
  1. `명령` → 기대 결과 (예: `npm test -w packages/core -- combat` → 12 passed)
  2. …
- 크기: S(<30분) / M(<1시간) / L(분할 고려)
- 참고: 함정·엣지 케이스

수용 기준 작성 규칙

  • 실행 가능한 명령 + 관측 가능한 결과. "동작해야 한다"는 기준이 아니다.
  • 코어 태스크는 유닛 테스트 개수와 핵심 케이스(경계값: L=0, s=1, 보스 시간 초과)를 명시.
  • 시뮬레이터 태스크는 시드 고정 시 동일 출력(결정성) 테스트를 포함.
  • 렌더러 태스크는 Playwright 스크린샷 파일 생성 + 콘솔 에러 0을 기준으로.
  • 밸런스 회귀는 목표 벽 표 대비 허용 오차(±10%)를 숫자로.

크기 판단

L이면 분할한다. 한 세션에 끝나지 않는 태스크는 코딩 에이전트가 중간 상태를 남기고 멈추기 쉽다.
