**분해에서 즉시 보이는 세 가지**
1. **아트(3+4+5)가 24~48인·일로 단일 최대 덩어리.** 회사가 아트를 먼저 요청한 이유가 여기서 수치로 설명된다.
2. **QA(10)와 배포 후 대응(12+13)을 합치면 14~29인·일.** 즉 "만드는 시간"만큼 "확인하고 수습하는 시간"이 든다. 요청 범위가 아트·QA인 것은 정확한 직관이다.
3. **2번(밸런스 테이블)과 10번(수동 QA)이 서로를 보완하지 못한다.** 곡선 검증이 배포 전에 없기 때문에, 2번의 실수가 12번의 핫픽스로만 드러난다. 이 고리를 끊는 것이 가장 큰 구조 변화다.

## 6. Quick Win 후보 3 (미팅 시연 화면 포함)

**선정 기준**: 도입 난이도 낮음 + 체감 높음 + 진단 기간(2~3주) 내 시제품 가능 + 기존 업무를 멈추지 않음.
**공통 원칙**: 세 가지 모두 **사람이 최종 승인**하는 구조로 만든다. 자동 발송·자동 반영은 없다.

### QW-1. 리뷰 신호 대시보드 — "23.7만 건을 처음으로 한 화면에서 본다"
| 항목 | 내용 |
|---|---|
| 해결 병목 | #5 배포 후 모니터링(점수 8), #11 리뷰 눈으로 훑기(2.0) |
| 무엇을 하는가 | 스토어 리뷰를 수집해 버전별·유형별로 자동 분류하고, 배포일 기준 불만 급증 구간을 표시 |
| 난이도 | **낮음** — 사내 시스템 접근 불필요. 미팅 전(D-7~D-1)에 이미 시제품 제작 가능 |
| 시제품 기간 | 3~5일 (미팅 전 완료) |
| **미팅 시연 화면 1장** | **"버전 타임라인 × 불만 클러스터 히트맵"** — 가로축은 3.40→3.50→3.60 배포일, 세로축은 결제/버그/밸런스/UX/CS/칭찬 6개 클러스터, 셀 색은 해당 구간 언급량. 3.60 배포일 직후 칸 하나가 붉게 뜨고, 그 칸을 짚으면 실제 리뷰 원문 3건이 뜬다. **화면 하단에 '이 회사의 8년치 유저 목소리'라는 한 줄만.** |
| 기대 반응 | "이만큼 알고 왔구나" — 신뢰 확보용 오프닝 자산이자 진단 데이터. 대표가 처음 보는 자사 데이터일 확률이 높다. |
| 주의 | 이 화면으로 **비난하지 않는다.** 붉은 칸을 짚되 "왜 이랬냐"가 아니라 "여기서 무슨 일이 있었나요"로 묻는다. |

### QW-2. CS 1차 답변 초안 + 결제 근거 자동 대조 — "템플릿 답변을 근거 있는 답변으로"

**세션 B 운영 규칙**
- 아트 세션·QA 세션은 **대표를 반드시 다른 방으로 보낸다.** "실무 디테일이라 대표님 시간을 아끼겠다"는 명분으로 자연스럽게. AI에 대한 진짜 감정은 대표 앞에서 나오지 않는다.
- 3.60 해부는 우리가 채우지 않는다. **그들이 채우게 하고 우리는 질문만 한다.** 우리가 채우면 그들의 인식이 아니라 우리의 가설이 기록된다.
- 숫자를 모른다고 하면 범위로 받는다. "정확히는 모르겠는데요" → "대략 2일입니까 5일입니까?"

## 8. 진단 계획서 (2~3주)

**목표**: 병목 점수표를 추정에서 실측으로 바꾸고, 기준선 지표 4개를 측정하고, Quick Win 1개를 가동 상태로 만든다.
**원칙**: 진단 기간에 고객의 업데이트 일정을 멈추지 않는다. 인터뷰는 1인당 60분을 넘기지 않는다.

원시인 형님들 키우기의 확인·추정 시스템 목록입니다: **문명 / 강화 / 합성 / 토템 / 슬롯머신 / 보스토벌 / 형님의 탑 / 길드 / 월드(3.60 신규) / 스킨(3.60 신규) / 탈것(3.60 신규) / 월드 몬스터 도감 / 카드(3.60 신규)**. 앞의 8개가 8년간 누적된 곱셈 구조이고, 3.60에서 5개가 **한 번에** 얹혔습니다. 신작이 계승할 것과 버릴 것을 판단할 때, 이 곱셈 누적이 후반 곡선을 어떻게 붕괴시키는지가 가장 중요한 학습 포인트입니다.
리뷰에서 확인된 UX 마찰: **보스토벌 기본 설정이 초기화되는 현상**(반복 진입형 콘텐츠에서 설정 지속성이 깨지면 방치형의 핵심 가치인 '손 안 대도 되는 것'이 무너집니다), **결제 3회 중 2회만 반영되는 미수령**, **"고객센터로 보내주세요" 수준의 GM 템플릿 답변**입니다. 추정 마찰로는 특정 구간 성장 벽, 뽑기·합성 확률 체감 불일치, 신규 콘텐츠 해금 조건 설명 부족이 있습니다.
반대로 유저가 꼽는 **최대 장점은 "8년간 큰 업데이트가 끊기지 않는다"이고, 과금 구조에도 우호적**입니다. 신작 설계에서 이 두 가지는 방어선입니다 — 콘텐츠 처리량과 온건한 과금이 이 IP의 정체성이며, 대형사가 같은 장르에 들어오는 상황에서 여기를 훼손하는 설계는 전작의 자산까지 깎습니다.

### → codex-build-planner (Codex 빌드 플래너): 추정 스택과 시뮬레이터-퍼스트 필요성

추정 스택(전부 미확인, 첫 미팅 검증 예정): 클라이언트 **Unity/C#**, 애니메이션 **Spine 또는 스프라이트 시트**, 밸런스 테이블 **Google Sheets → CSV/JSON 익스포트(일부 수동)**, 서버는 자체 서버 + RDB 계열, CS는 **Freshdesk**, 형상관리 Git + 수동 빌드, **자동화 테스트 0개**. Windows 빌드가 존재하므로 멀티 타겟 구성입니다.
가장 중요한 미확인 항목은 **U-06: 전투·성장 계산이 화면 갱신 코드와 분리되어 있는가**입니다. 8년 라이브 프로젝트의 전형대로 혼재되어 있을 가능성이 높고, 그렇다면 순수 로직 추출 리팩터링이 모든 QA 자동화의 선행 조건이 됩니다. 이 값 하나로 일정이 몇 주 단위로 달라지므로, 빌드 계획은 **분리됨/혼재됨 두 갈래로 준비**해 주십시오.
시뮬레이터-퍼스트가 필요한 이유는 장르 구조 때문입니다. 문명·강화·합성·토템에 월드·탈것·카드 배수가 곱해지는 구조에서 한 상수의 변경은 200스테이지 뒤에 벽으로 나타나며, **사람이 손으로 플레이해 확인하는 것이 물리적으로 불가능**합니다. 화면 없이 로직만 수천~수만 판 돌려 성장 곡선을 배포 전에 산출하는 것이 병목 1·3·5위를 한꺼번에 푸는 유일한 경로입니다.
시뮬레이터가 서면 그 위에 세 가지가 바로 얹힙니다: **결제→검증→지급 회귀 시나리오**(리뷰에서 확인된 매출 직결 이슈), **확률 표기값-구현값 자동 대조**(규제 대응이자 경영진 설득 카드), **밸런스 변경 전후 곡선 diff 리포트**. 빌드 순서는 로직 추출 → 결정론적 실행 환경 → 회귀 시나리오 → 곡선 리포트를 권합니다.
